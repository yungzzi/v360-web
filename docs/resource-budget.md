# 资源预算

当前 Compose 面向共享小型 Linux 服务器。下面是应用限制和存储策略，不是为整个主机预留的独占资源；部署到其他机器仍需核对实际可用容量及其他服务负载。

## 内存、CPU 和进程

[compose.yaml](../compose.yaml) 将后端、摄像头 SDK 工作程序及媒体处理子进程限制在同一容器：

| 项目 | 限制 |
| --- | --- |
| CPU | 1.0 CPU 时间额度，不绑定单个核心 |
| 内存 | 768 MiB 硬上限 |
| 内存加交换空间 | 同为 768 MiB，即不允许额外使用 swap |
| 进程数 | 256 |
| 临时内存目录 | `/tmp` 最多 64 MiB，计入内存用量 |
| Docker 日志 | 最多三份、每份 10 MiB |

Compose 没有设置早期设计中的 512 MiB 内存压力阈值，也没有承诺固定最低可用内存。到达硬上限可能使进程被终止；需观察 OOM 和重启记录，不能把容器健康检查当成设备在线证明。

一个后端进程、一个摄像头连接、一个转换任务；最多三个同镜头观看窗口共享输出，不为每位观众新开转换器。不同镜头并行观看、多个 worker 或生产实例不属于支持范围。观看优先，可能推迟自动取片。

## 磁盘

服务器档：原片、完整/分段网页文件、直播缓存合计最多 **15 GiB**，不是每类各 15 GiB。默认年龄保留期三十天，空间不足会更早清理；先保护锁定、使用中和未完成文件，无法安全清理时停止新增。

每次准入及持续写入检查文件系统实际空闲量，保留至少 **8 GiB** 给系统和其他应用。该底线与 15 GiB 上限同时生效，磁盘不足时不为达到上限而继续下载。这是应用层检查，不是分区、预分配文件或 Docker 硬磁盘配额。

私有运行依赖、SQLite、元数据备份、镜像层和构建缓存不包含在媒体的 15 GiB 中，需要额外核算。只保留必要镜像与备份；不能对共享主机随意执行全局 Docker 清理。备份工具不自动删除旧快照。

十五天需要多少空间取决于每天实际录像总时长及压缩效果。早期样本估计两份文件合计 15 GiB 接近两周，只是估算，不是保存天数承诺；以实际日增量、最早仍可回放日期和清理状态为准。

## 部署验收

已有 Docker 本地和云端部署经验，但单次峰值采样不代表长期预算。新环境需核对 cgroup 实际限制、磁盘增长、持续观看、自动保存及其他服务响应。优先降低并发或后台负荷，不自动提高资源上限，也不修改摄像头工作模式。
