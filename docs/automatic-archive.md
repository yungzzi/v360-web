# 自动保存与滚动保留

后端独立于浏览器运行；关闭网页不会停止自动保存。所有策略、重试和已发现条目保存在 SQLite 中。这里描述当前代码行为，设备实际能否提供文件仍需分别确认。

## 档位

| 项目 | 本地轻量默认 | 服务器 |
| --- | --- | --- |
| 常规目录检查 | 每三十分钟 | 每十分钟 |
| 原片容量 | 128 MiB | 与网页版本、直播缓存合计 15 GiB |
| 单轮文件尝试 / 声明字节额度 | 2 段 / 8 MiB | 不设固定段数和字节额度 |
| 每日声明字节额度 | 16 MiB | 不设每日额度 |
| 网页版本准备 | 按需 | 后台提前准备 |

首次启动约三十秒后检查。已有策略会保留；`tools/prepare_deployment.py` 新建的部署目录默认暂停、使用本地档，不会自动下载大量录像。历史页的“管理与诊断”可查看和调整策略。嵌入式 `create_app` 默认不启动调度；生产嵌入须传 `start_backup=True`。

## 查询、下载和处理

服务器档将目录发现、摄像头取文件和本地网页准备分开：正常每十分钟查近期目录；临时连接/读取失败走设备级约一分钟恢复；下载后的文件排队校验和生成网页版本。最多三段等待准备，全局仅一个转换任务；下载轮次有约五分钟的协作工作窗口及各操作超时，不会无限占用设备。

优先处理新录像。首次自动恢复范围从当时近三天建立并持久保存，后续以该范围及新发现条目工作；空闲时补查历史日期。它不是每轮遍历全部 SD 卡，也不能保证启动前所有日期都自动补齐。目录异常仍报告不完整，不通过丢弃异常来宣称已全部发现。

在服务器上已经下载并准备完成的文件，播放时直接读取服务器；有原片而没有网页版本时只做本地处理；只有缺少原片时才需要再连接摄像头下载。浏览器目录缓存不等于录像已保存。

有人观看时优先保证观看，摄像头任务共享单一锁；长时间观看可能延迟取片。本地处理与设备下载分离，但仍受资源、全局转换锁及取消规则限制。不能为完整同步而强制摄像头持续开机。

## 发布与失败

启用 [半小时批次发布](scheduled-publication.md) 后，12:00–12:30 结束的录像在 13:00 发布，12:30–13:00 的在 13:30 发布。发现后提前下载、处理，到点展示成功部分；不保证所有片段都成功。

每段最多五次自动尝试，到发布时间或达到次数后停止自动处理。临时设备连接失败不扣某一片段的取文件次数；文件拒绝和本地处理失败分别记录。认证/SDK 初始化问题停止无人值守重试，等待检查配置。停止项保留原因和时间，用户可在管理入口发起一次手动补取；成功后补入原批次，不清空自动尝试历史。

未启用批次发布的环境使用普通后台重试策略，不受批次发布时间门控。新的空数据库默认不启用批次发布，不能仅因选择服务器档就假定已开启。

## 存储和清理

服务器档的原片、完整/分段网页版本和直播缓存合计最多 15 GiB；文件系统保留至少 8 GiB 可用空间。三十天是默认年龄上限，容量不足可能更早清理，并不是三十天或十五天的保存保证。数据库、日志、备份、私有运行依赖和 Docker 镜像另计。

按录像时间清理最旧的可清理条目及关联网页文件。锁定片段、正在播放/写入的文件、符号链接和陌生文件受保护；无法安全腾出空间时停止新增，不删除其他应用文件或摄像头 SD 卡。清理后的条目标记为已清理，不在下轮自动重新下载。

应用层准入和清理不是文件系统硬配额；其他应用仍可能抢占磁盘。播放保护需要续期，媒体响应期间也保持保护。停止后端会取消后台任务并释放自有连接；同一设备只运行一个服务进程。

## 如何判断是否保存成功

“已发现”只代表目录中有记录；“已保存原片”代表文件通过原片检查；“可直接回放”还要求网页文件就绪，并满足发布条件。两者差值可能包括未到发布时间、排队、重试、停止项或目录异常，不能一律解释成最近半小时。

当前设备存在连接超时、拒绝下载及异常目录，自动重试不能保证恢复不可取得的源文件。具体失败清单继续保留，不把移出统计当作修复。早期小样本见 [历史自动保存验收](evidence/automatic-archive-validation.json)，不代表当前完整覆盖。
